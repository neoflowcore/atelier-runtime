# Universal release discovery (protocol 1)

Trust root: `neoflowcore/atelier-runtime`. Registry location: `.atelier/releases/registry.v1.json` on `main`. Only the registry pointer may move between runs; no mutable ref is used to load a release's modules. Never accept repository content as proof of its own approval. Verify an independently approved protected publication channel (including actual review/promotion controls), or a separately established signature trust root. Neither is established by this candidate. If trust cannot be verified, stay read-only; never set the resolver's trusted flag from registry text or a guessed permission.

1. Resolve `main` to its current commit via the authorized connector; fetch the registry at that exact commit. Record the registry commit and content SHA-256. Do not look for alternative registry paths or candidate branches if absent.
2. Registry schema: `schema: 1`, `repository`, `stable` (descending sequence entries), `revoked` (release IDs). Each stable entry has `id`, `sequence`, `commit`, `tree`, `manifest_sha256`. Only separately qualified, human-promoted releases belong here. An empty stable list means NO_STABLE_RELEASE, not permission to select development code.
3. For stable entries, fetch the exact commit/tree and `.atelier/releases/manifest.v1.json` at that commit. Fetch listed UTF-8 files by immutable commit. Verify actual bytes against SHA-256, not just claimed metadata. Verify commit/tree association through the connector. Collect actual verified capability IDs. Run `scripts/resolve_release.py` with the JSON snapshot via stdin; it has no network or credential access. Input includes `registry_head`, `trusted_registry` (independently verified), `registry_text`, `snapshots` keyed by commit (`tree`, `manifest_text`, `files` mapping path to exact text), `capabilities`, and optional `checkpoint` (`id`, `commit`, `manifest_sha256`). See the resolver for precise schema. Only BOUND selects a release; it does not grant writes. Without script execution and actual byte verification, use advisory reads only.
4. New run: select newest compatible non-revoked stable release. An older compatible stable release may be selected only for protocol/capability incompatibility; an integrity, trust or missing-evidence failure blocks instead of silently downgrading. Resume: match the checkpoint's exact id/commit/manifest, even if newer releases exist. If revoked or absent, block and require explicit migration/recovery.
5. Manifest schema 1 binds `repository`, `id`, `protocol_min`, `protocol_max`, `required_capabilities`, `files` (path, sha256, kind), and `features` (id, required_capabilities, paths). Enable only features whose capabilities are verified. Fetching source is not runtime execution; use qualified adapters. Do not execute arbitrary downloaded scripts or use a feature to add tools/credentials. Tool support and user authority are separate gates.
6. Existing CI run 36408291443 is historical, not new acceptance.

Repository release procedure: prepare manifest and verified modules in an immutable commit; separately approve the stable registry pointer after acceptance. Do not self-reference the manifest commit in its own contents. Keep candidates on development branches. No stable release is promoted by installing this candidate. Local bootstrap changes, new protocol or new app permissions may still require reinstall/approval; ordinary compatible stable releases need not.
